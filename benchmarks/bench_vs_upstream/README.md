# fastcellstates vs. the original cellstates

Compares this fork against the original
[`cellstates`](https://github.com/nimwegenLab/cellstates) on the same real
dataset: wall time, peak memory, resulting state count, and final
log-likelihood. Feeds `docs/_static/benchmark_vs_upstream.svg`, referenced
from `docs/changes.md`.

## Layout

```txt
scripts/                  the actual work, tool-agnostic to how it's invoked
  prepare_data.py           fetch/filter a dataset -> shared dense (G, N) .npy
  run_fastcellstates.py      one fastcellstates config -> results/<name>.json
  run_upstream.py            one original-cellstates run -> results/<name>.json
  render_table.py            results/*.json -> the SVG table (+ a markdown copy to stdout)
slurm/                     thin sbatch wrappers around the scripts above
  job_prepare.sbatch
  job_fastcellstates.sbatch
  job_upstream.sbatch
  job_render.sbatch
submit_jobs.sh             SLURM entry point: submits the scripts above as
                            independent, dependency-chained jobs
run_all.sh                 non-SLURM entry point: runs everything locally,
                            in sequence (for a quick check without a cluster)
upstream_cellstates/       a separate, independently-solved pixi env (its own
                            pixi.toml / pixi.lock) with the original
                            `cellstates` pip-installed from GitHub: it needs
                            isolation from the main dev environment
                            (numpy<2, Cython, an older dependency set)
_data/                     shared input, gitignored (regenerated by prepare_data.py)
results/                   per-run JSON, tracked; slurm-*.out logs, gitignored
                            (byte-identical to the JSON, and named after a
                            volatile job id)
```

Every script in `scripts/` is also directly runnable on its own (each has a
usage example in its docstring) if you only want to rerun one thing.

## Running it

On a SLURM cluster (the intended path):

```sh
bash benchmarks/bench_vs_upstream/submit_jobs.sh
bash benchmarks/bench_vs_upstream/submit_jobs.sh --only fast,upstream
bash benchmarks/bench_vs_upstream/submit_jobs.sh --upstream-threads 1,4,8,16
bash benchmarks/bench_vs_upstream/submit_jobs.sh --h5ad /path/to/data.h5ad \
    --data benchmarks/bench_vs_upstream/_data/mine.npy
```

This submits `prepare -> {fastcellstates configs, upstream thread counts}
in parallel -> render` as separate jobs, chained with `--dependency` so
nothing starts before its data exists and the table only renders once
everything else has finished. Track with:
`squeue -u $USER -o '%.10i %.25j %.8T %.10M %N %R'`.

Without SLURM, `run_all.sh` runs the same steps locally and sequentially
(slower, but no cluster needed) with the same flags.

## Methodology notes

A few choices here aren't obvious from the code alone, and matter for
trusting the numbers:

- **Same hardware family for every job.** `submit_jobs.sh` auto-detects the
  largest homogeneous (same vendor/CPU/RAM feature tags) schedulable node
  family and passes it as `--constraint` to every job. This cluster is not
  hardware-uniform (node families here span Intel Ice Lake vs. AMD, and
  different core/RAM sizes), so without this a job could land on a faster
  or slower machine than the one it's being compared against, confounding
  "which tool is faster" with "which node did you get." Jobs still land on
  *different* physical machines within that family (not pinned to one
  node), so they don't compete with each other for one node's shared
  memory bandwidth/cache either.
- **Same `--cpus-per-task` for every job**, fixed in the `slurm/job_*.sbatch`
  files (currently 16), regardless of how many threads a given run is
  actually told to use. Each tool's own thread/thread-count setting still
  caps how many it actually spawns (cellstates's OpenMP `num_threads`,
  fastcellstates's numba default), so idle allocated cores beyond that
  don't change what's measured; a uniform allocation is simpler than
  sizing each job individually.
- **Each tool at its own default end-to-end behaviour**, not an artificially
  matched setting. Both fit Theta by default (fastcellstates via
  `log_search`, the original via its own `--prior-optimization`, on by
  default); neither run is forced to a fixed Theta. Similarly, the original
  defaults to 1 thread and fastcellstates defaults to using every core it
  sees; `--upstream-threads` sweeps the original across several thread
  counts explicitly (its own default, 1, is one of the rows) rather than
  silently equalising it away, since the "as shipped" comparison is the
  honest one, and the sweep shows the effect of that setting directly.
- **fastcellstates gets sparse input, the original gets dense.** The shared
  data is a dense `.npy` (the one format both readers agree on), but
  `run_fastcellstates.py` converts it to a sparse CSC matrix before timing,
  matching fastcellstates's actually-recommended usage (reading straight
  from `.h5ad`, never densified). This isn't cosmetic: `Cluster.__init__`
  rebuilds its internal sparse structure from scratch on every Theta probe,
  so dense input would pay a full nonzero-scan on every single probe. The
  original has no sparse code path at all (its own `.mtx` loader calls
  `.toarray()` immediately), so dense is its only real mode.
